# 173 - Release Artifacts and Provenance

**Concepts:** stamping, SBOMs, supply-chain metadata

## Run it

```bash
R=//173_release_provenance

bazel build --config=release $R:release
tar tzf bazel-bin/173_release_provenance/release.tar.gz
```

## What provenance means

An artifact in production should be able to answer, without anyone guessing:

1. **What is it?** Name and version.
2. **Where did it come from?** The exact source commit.
3. **What is inside it?** The full dependency list.
4. **How was it built?** Bazel version, flags, platform.
5. **Who built it?** CI system and invocation ID.

Bazel can answer all five, because all five are properties of the build graph.

## 1-2: Stamping (sample 092)

```bash
bazel build --config=release //...:release
```

```
build:release --stamp
build:release --workspace_status_command=./tools/workspace_status.sh
```

The manifest in this sample embeds `STABLE_GIT_COMMIT`, so the tarball names
its own source revision.

## 3: The dependency list, from the build graph

```bash
bazel query "deps(//173_release_provenance:release)" \
  --output=label_kind > dependencies.txt

# External modules only
bazel query "deps(//...:release)" --output=package | grep '^@' | sort -u
```

Or make it an artifact with `genquery` (sample 094), so the dependency list is
built and shipped alongside the binary rather than generated by a separate
script that can drift.

## 4-5: The build itself

The BEP (sample 156) records the Bazel version, the full command line, the
configuration, and an invocation ID:

```bash
bazel build //...:release --build_event_json_file=/tmp/bep.json
jq 'select(.started) | .started' /tmp/bep.json
```

Archive that JSON next to the artifact and the build is fully described.

## SBOMs

`rules_license` (a dependency of this repo) propagates license metadata through
the graph, and an **aspect** (sample 130) can walk the dependency closure
collecting it - which is exactly how SBOM generators for Bazel work.

```python
package(default_applicable_licenses = ["//:license"])
```

The general shape: an aspect over `deps` gathering `LicenseInfo`, aggregated
into an output group, emitted as SPDX or CycloneDX.

## SLSA

Bazel's properties map directly onto SLSA build-provenance requirements:
scripted build, declared inputs, isolated execution (the sandbox),
reproducibility, and a machine-readable record (the BEP). Most of the work for
higher SLSA levels is CI attestation on top of what the build already produces.

## Key takeaway

Provenance is derivable from the build graph. Stamp the commit, emit the
dependency list as an artifact, and archive the BEP.
